# 04. 단계별 추진 계획

> 문서 상태: 초안 (v0.1, 2026-10-13)
> 기간과 인력은 추정치입니다. Phase 0 결과로 다시 산정합니다.

## 1. 전체 일정

| 단계 | 기간(추정) | 목표 | 판정 |
|---|---|---|---|
| Phase 0. 사전 확인 | 1~2주 | 전제 조건 검증 | 진행 가능 여부 |
| Phase 1. PoC | 3~4주 | 조회 업무 1건 자동화로 기술 가능성 입증 | Go / No-Go |
| Phase 2. MVP | 6~8주 | 쓰기·승인 포함 핵심 유즈케이스 4종 | 파일럿 진입 여부 |
| Phase 3. 파일럿 | 8주 | 1개 부서 실사용, 데스크탑 클라이언트·Hub | 확산 여부 |
| Phase 4. 확산 | 지속 | 부서·스킬 확대, 운영 체계 정착 | - |

## 2. Phase 0 — 사전 확인

코드를 쓰기 전에 전제를 확인한다. 하나라도 막히면 설계를 조정한다.

| 확인 항목 | 방법 | 담당 |
|---|---|---|
| Gemma API 스펙 | 툴 호출·JSON 출력·이미지 입력 지원, 컨텍스트 길이, 응답 속도, 할당량을 실측 | 개발 |
| 모델 기초 능력 | 실제 화면 스냅샷 10개로 "다음에 누를 요소 고르기" 정답률 측정 | 개발 |
| 보안 정책 | 확장 설치, `debugger`·`nativeMessaging` 권한, 로그 범위 협의 | PI + 보안 부서 |
| 대상 시스템 | UC-01 대상 화면의 UI 구조(표준 HTML/전용 그리드) 조사 | 개발 + 현업 |
| 현업 기준선 | 대상 업무의 현재 건당 소요 시간, 월 빈도, 수행 인원 조사 | PI + 현업 |

**산출물**: 사전 확인 결과서, 조정된 요구사항·일정.

## 3. Phase 1 — PoC

**범위**: UC-01 재공 확인. 확장 단독 구성.

| 작업 | 내용 |
|---|---|
| 확장 골격 | Side Panel, Service Worker, Content Script |
| 화면 스냅샷 | 요소 번호 부여, iframe 처리, 그리드 요약 |
| 에이전트 루프 | Gemma 연동, 스키마 검증·재시도, 중단 조건 |
| 기본 도구 | navigate, click, type, select, wait_for, extract_table, write_excel |
| 스킬 런타임 | 스킬 문서 로딩, 단계 추적, 검증 조건 |
| 통제 | 허용 도메인, 로컬 감사 로그, 중지 버튼 |
| 모의 사이트 | 대상 화면과 같은 구조의 테스트용 페이지 (개발·회귀 테스트용) |

**Go 기준**

- UC-01 동일 조건 20회 반복 성공률 90% 이상
- 추출 데이터가 화면 값과 100% 일치
- 건당 소요 시간이 수작업보다 길지 않음
- 보안 부서의 PoC 구성 승인

**No-Go 시 대안**: 성공률이 낮은 원인이 모델이면 더 좁은 역할(요소 선택만)로 축소하거나 경로 캐시 비중을 높인다. 원인이 화면 구조면 사이트 어댑터를 먼저 개발한다.

## 4. Phase 2 — MVP

**범위**: UC-02 웹→엑셀 가공, UC-03 엑셀→웹 입력, UC-05 방화벽 신청, UC-07 스킬 관리.

| 작업 | 내용 |
|---|---|
| 데이터 | Dataset Store, 엑셀 읽기, 가공 엔진, 대조(compare) |
| 입력 | paste_table (붙여넣기·셀 단위), 다운로드 처리, 팝업·새 탭 |
| 승인 | R3 판정 규칙, 승인 대화상자, 드라이런 모드 |
| 정책 | 입력값 정책 검증 (방화벽 신청 규칙) |
| 안정화 | 경로 캐시, 자가 복구, 스크린샷 보조 입력 |
| 스킬 | 스킬 명세 확정, 스킬 4~5종 작성, Git 리뷰 절차 |
| 스킬 제작 체계 | 조작 녹화로 초안 생성, 품질 검사(등급), 초안 시험 실행, 배포 관문 ([06-skill-authoring.md](06-skill-authoring.md)) |
| 배포 | 서명, 사내 파일 서버 게시, 정책 설치 (canary 채널) |

**파일럿 진입 기준**

- 4개 유즈케이스 각각 반복 성공률 90% 이상
- 쓰기 유즈케이스에서 승인 없는 제출 0건, 입력 대조 불일치 상태의 승인 요청 0건
- 방화벽 신청 유즈케이스에 대한 보안 부서 승인
- 현업 5명 내외 사용성 테스트 완료
- 개발자가 아닌 현업 엔지니어 2명 이상이 녹화로 스킬을 만들어 품질 등급 B 이상, 시험 실행 통과까지 도달

## 5. Phase 3 — 파일럿

**범위**: 1개 부서 실사용. UC-04 다중 시스템 리포트, UC-06 스케줄.

| 작업 | 내용 |
|---|---|
| 데스크탑 클라이언트 | Electron 앱, Native Messaging, 에이전트 코어 이전 |
| 파일·스케줄 | 폴더 접근, 엑셀 템플릿 채우기, 스케줄러 |
| 스킬 배포 | Git 동기화, 개인/공용 스킬 구분 |
| Hub | 정책 배포, 로그 수집, 통계 대시보드, kill switch |
| 스킬 제작 확장 | 표 페이지 넘김·일괄 입력 녹화, 초안 공유(동기화), 스킬별 성공률로 화면 변경 감지 |
| 운영 | pilot 채널 배포, 문의 대응 절차, 스킬 오너 지정 |

**확산 기준**

- 파일럿 부서 주간 활성 사용자 비율, 스킬별 성공률이 목표치 이상 (목표치는 Phase 2 종료 시 설정)
- 실측 절감 시간이 Phase 0 기준선 대비 유의미
- 보안 사고·오제출 0건

## 6. Phase 4 — 확산

- 부서별 스킬 오너 양성, 스킬 제작 교육 (녹화 → 검사 → 시험 실행 → 배포 요청)
- 스킬 카탈로그 운영 (검색, 사용 통계, 평가)
- API가 있는 시스템은 MCP 커넥터로 전환해 속도·안정성 개선
- Gemma 버전 업그레이드 대응 (회귀 테스트 자동화)

## 8. 효과 측정 방법

효과 수치는 가정하지 않고 측정한다.

```
월 절감 시간 = Σ (스킬별 수작업 건당 시간 − 에이전트 사용 시 사람 개입 시간) × 월 실행 건수
```

- **수작업 건당 시간**: Phase 0에서 현업 인터뷰·실측으로 확보
- **사람 개입 시간**: 지시 입력, 승인, 결과 확인에 쓴 시간 (실행 로그에서 산출)
- **월 실행 건수**: 실행 로그

부가 지표: 입력 오류 건수 변화, 스킬 성공률, 화면 변경 후 스킬 복구까지 걸린 시간.

## 9. 리스크

| 리스크 | 영향 | 대응 | 확인 시점 |
|---|---|---|---|
| Gemma의 툴 호출·다단계 판단이 불안정 | PoC 실패 | 스킬 주도 구조, 스키마 재시도, 경로 캐시로 모델 의존 축소 | Phase 0~1 |
| 대상 시스템이 전용 그리드 프레임워크 | 추출·입력 불가 | 사이트 어댑터, 스크린샷 보조, 화면의 엑셀 다운로드 기능 활용 | Phase 0 |
| 확장 권한이 보안 정책에 막힘 | 구조 변경 | content script 전용 축소안, 조기 협의 | Phase 0 |
| 잘못된 저장·상신 | 업무 사고 | 승인 게이트, 입력 대조, 드라이런, 감사 로그 | Phase 2 |
| 화면 변경으로 스킬이 깨짐 | 운영 부담 | 자가 복구, 성공률 모니터링, 스킬 오너 체계 | Phase 3~ |
| 모델 응답이 느려 수작업보다 오래 걸림 | 사용 안 함 | 경로 캐시로 호출 축소, 스냅샷 압축 | Phase 1 |
| 스킬 작성이 어려워 확산 정체 | 효과 제한 | 녹화로 초안 생성, 틀(`skill:new`), 교육 | Phase 2~ |
| 만든 사람마다 스킬 품질이 다름 | 실패·오제출 | 품질 검사 규칙과 등급, 시험 실행을 거쳐야 배포 요청 가능 | Phase 2~ |

## 10. 의사결정 요청 사항

1. Phase 0~1(약 5~6주) 착수 승인과 개발 인력 2명 배정
2. PoC 대상 시스템(재공 조회)과 현업 담당자 지정
3. 보안 부서 협의 창구 지정
4. 사내 Gemma API 개발용 할당량 확보
