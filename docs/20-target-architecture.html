Dogent 목표 아키텍처

2026-11-03 · 현재 구현(docs/19)과 "서버 쪽에 더 필요한 것"을 구분해 그린 제안 문서입니다. 점선 주황 상자는 아직 없는 제안입니다.

1. 먼저 결론

Dogent는 "각자 PC에서 도는 에이전트"가 본체이고, 서버는 그것을 보조하는 얇은 계층입니다. 로그인 세션, 승인 창, 사내 화면 조작, NASCA 문서가 모두 사용자 PC에 묶여 있어서 실행을 서버로 옮기면 오히려 안전장치가 약해집니다. 그래서 서버에는 "공유해야 하는 것"(스킬, 시스템 사전, 정책)과 "모아야 하는 것"(실행 기록, 신고, 통계)만 둡니다.
지금 파일럿 규모라면 필요한 것
  • 사내 GitHub (스킬·사전 저장소) — 있음
  • 시스템 사전 MCP 서버 1대 (VM이면 충분)
  • 배포 묶음을 올릴 파일 서버
  • 사내 Gemma 게이트웨이 — 있음

k8s, DB, 메시지 큐는 아직 필요 없습니다.

사용자가 늘고 운영이 필요해지면 더할 것
  • Hub: 정책 배포, 중지 스위치, 실행 기록 수집, 통계 (→ PostgreSQL)
  • LLM 프록시: 키를 PC에서 빼고 사용자별 한도·감사
  • SSO 연동, 관측(로그·지표), 백업
  • 이벤트 전달: 처음엔 폴링, 필요해지면 버스

서비스가 3개 이상이고 가용성 요구가 생길 때 k8s가 의미가 있습니다.

2. 지금 구조 (구현된 것)

서버라고 부를 만한 것은 시스템 사전 MCP 서버(만들어 두었으나 아직 설치 전) 하나뿐이고, 나머지는 모두 PC 안에서 돌거나 기존 사내 인프라(GitHub, Gemma)입니다.

구현·시험됨 구현됨, 연결 미흡 기존 사내 인프라·외부 제안 (없음)

현재 비어 있는 것: 정책 배포, 중지 스위치, 실행 기록 수집, 사용자별 모델 키·한도, 중앙 통계, 설치 판 관리(canary). 모두 서버가 있어야 풀리는 문제입니다.

3. 목표 구성도

PC 쪽은 그대로 두고, 가운데에 "Dogent 서비스 영역"을 더합니다. 실선은 호출, 점선은 약한 결합(캐시·폴링)입니다.

구현·시험됨 구현됨, 연결 필요 기존 사내 인프라·외부 제안 (없음)

배포 묶음(zip)은 사용자가 PC에 설치하는 경로이며, 서비스가 아니라 파일 서버 → PC 방향의 별도 경로입니다.

5. 주요 흐름

5-1. 요청 실행 (런타임) — 서버를 거치지 않는 경로가 기본

① 요청사용자가 앱에 말로
→
② 로컬 해석캐시된 스킬·사전으로 시스템과 스킬 선택
→
③ 모델 호출Gemma 직접, 또는 LLM 프록시 경유
→
④ 화면 조작브리지 → 확장 → 사내 웹. 승인 창은 PC에서
→
⑤ 결과엑셀·보고서를 PC에 저장
→
⑥ 요약 전송실행 요약만 Hub로 (값·화면 글자는 제외)

서버가 죽어도 ①~⑤는 캐시로 계속 돕니다. 서버 장애가 업무 중단이 되지 않게 하는 것이 핵심 원칙입니다 (Hub와 사전 서버는 없어도 동작, 있으면 더 좋음).

5-2. 스킬·사전 게시 (콘텐츠 흐름)

담당자PR 작성
→
CI 검사스킬 품질, 사전 형식·중복·도메인
→
CODEOWNERS 승인부서 담당 리뷰
→
main 병합정본 확정
→
게시스킬: index.json 생성 / 사전: MCP 서버 pull
→
클라이언트 반영스킬·사전 모두 1시간 폴링(ETag) + 로컬 캐시

콘텐츠의 정본은 Git 하나입니다. DB에 스킬을 따로 저장하지 않습니다 (이중 정본 방지).

5-3. 정책·중지·기록 (운영 흐름)

관리자정책 변경 / 스킬 중지
→
HubDB 저장, 버전 올림
→
클라이언트 폴링ETag로 변경 확인 (예: 1~5분)
→
즉시 적용다음 실행 전에 정책 검사, 중지된 스킬은 거절
→
기록 전송실행 요약 → Hub → 통계·알림
중지 스위치는 "닿지 못할 때"가 약점입니다. PC가 Hub에 닿지 못하면 중지가 적용되지 않습니다. 정책 응답에 만료 시간(TTL)을 두고, 만료 뒤 Hub에 못 닿으면 쓰기(R3) 스킬은 막는 방식을 권합니다. 조회(R1)는 계속 허용해 업무 중단을 줄입니다.

6. k8s 배치 (서비스 영역을 클러스터에 올릴 때)

사내에 k8s 플랫폼이 이미 있고 운영 팀이 있을 때의 구성입니다. 없으면 "6-2 단순안"으로 시작해도 됩니다.

6-1. 서비스별 설정 요점

서비스복제상태헬스체크외부 의존메모
systems-mcp2없음(읽기 전용, 신고만 파일/DB)GET /healthGit(읽기)이미 만든 서버. 컨테이너로 감싸고 신고 파일은 PVC 또는 Hub API 호출로 교체
skill-index2없음index.json 응답Git 또는 CI 게시지금처럼 GitHub raw를 쓰면 이 서비스는 생략 가능
hub-api2DB/health + DB 핑PostgreSQL, SSO정책 응답은 ETag·TTL, 기록 수신은 멱등(실행 id)
llm-proxy2Redis(한도)/healthGemma, Redis, 비밀 저장소스트리밍 응답 지원 여부 확인, 타임아웃은 클라이언트보다 길게
worker1DB작업 큐 깊이DB, 메신저/메일실패한 작업 재시도와 중복 방지

6-2. k8s가 없거나 작게 시작할 때 (단순안)

  • VM 1~2대 + docker compose(또는 systemd): systems-mcp, hub-api, PostgreSQL 컨테이너, 앞단에 사내 리버스 프록시.
  • DB는 가능하면 사내 DB 서비스를 쓰고 VM에는 앱만 둡니다 (백업·복구를 직접 안 하려고).
  • 서비스가 늘고 무중단 배포·자동 복구가 필요해질 때 k8s로 옮깁니다. 컨테이너 이미지를 처음부터 쓰면 옮기는 비용이 작습니다.

7. 데이터 모델과 이벤트

7-1. PostgreSQL 테이블 (Hub, 최소안)

테이블주요 칼럼용도
usersid(SSO), 부서, 마지막 접속, 판(버전), 상태누가 어떤 판을 쓰는지
runsrun_id, user_id, skill_id·판, 위험도(R1~R3), 결과, 시작·소요, 모델 호출 수, 오류 분류, 승인 여부실행 요약 (값·화면 글자·표 내용은 저장하지 않음)

policiesversion, 내용(JSON), 만료(TTL), 작성자, 시각사이트 허용 상한, 쓰기 허용 스킬, 입력값 정책

개인정보·업무 데이터를 서버로 올리지 않는 것이 원칙입니다. 실행 요약에는 표의 값, 입력한 신청 내용, 화면 글자를 넣지 않습니다. 승인 이력은 "승인했다/안 했다"와 스킬·시각만 남깁니다. 이 범위는 보안 부서와 합의한 뒤 확정하세요 (docs/19 확인 목록 C8, C26).

이벤트발행자구독자처음 방식나중 방식

7-3. 이벤트 버스를 언제 도입하나

상황선택
사용자 수십~수백 명, 이벤트가 분당 수십 건 이하버스 없이 HTTPS + DB + 폴링. 워커는 DB를 주기적으로 조회
비동기 처리(알림·집계)가 늘고 Redis가 이미 있음Redis Streams 또는 DB의 작업 큐 테이블
사내에 Kafka/NATS 표준과 운영 팀이 있고 여러 시스템이 같은 이벤트를 써야 함그 표준 버스에 합류 (Dogent가 새로 운영하지 않음)

클라이언트는 PC에서 시작하는 연결만 쓰는 편이 방화벽에 안전합니다. 서버가 PC로 먼저 연결하는 구조(푸시용 포트 열기)는 피하고, PC가 서버로 폴링하거나 장기 연결을 맺습니다.

8. 보안·운영

영역원칙구체
신원사내 SSO 하나Hub·관리 화면은 OIDC. 클라이언트 → Hub는 사용자 토큰(만료 짧게). 지금의 user-id 헤더는 신뢰하지 않고 서버에서 확정
권한역할 분리일반 사용자(기록 전송), 스킬 담당자(자기 스킬 통계), 사전 관리자(정책·중지), 감사자(읽기 전용)
비밀PC에 키를 두지 않기LLM 키는 프록시/비밀 저장소. 그 전까지는 빌드에 든 키가 노출될 수 있음을 인정하고 배포 범위를 제한
네트워크사내망 한정, 최소 허용NetworkPolicy, 서비스 → DB/Git/Gemma만. PC → Hub는 HTTPS 단일 진입점
데이터최소 수집7-1의 원칙. 로그에 값·화면 글자 금지. 보관 기간(예: 90일)과 삭제 작업을 정해 둠
변조 방지콘텐츠는 서명·해시스킬 인덱스의 해시 검증(지금 있음), 배포 묶음 서명, 정책 응답 서명
가용성서버 없이도 돈다클라이언트는 캐시로 동작, 정책 TTL 만료 시 R3만 차단 (5-3)
백업·복구복구를 시험DB 일일 백업 + 복구 훈련, Git이 정본이라 콘텐츠는 재생성 가능
변경 관리배포 채널canary → pilot → stable 판. 서비스는 롤링 배포와 롤백 절차
관측핵심 지표만Hub 오류율·지연, 기록 수신 실패율, 정책 폴링 실패 PC 수, 스킬별 성공률, 429 비율

10. 만들지 않는 것을 권하는 것

안 만들 것이유대신
서버에서 브라우저를 대신 돌리는 실행 서버 (헤드리스 워커 풀)사내 SSO 세션·OTP, 사람 승인 창, NASCA 문서가 모두 사용자 PC에 묶여 있음. 서버 실행은 안전장치(승인)를 약하게 하고 계정 공유 문제를 만듦예약 실행은 지금처럼 사용자 PC의 작업 스케줄러. API가 있는 시스템은 MCP 커넥터로 전환 (docs/04 6절)
스킬을 DB에 저장·편집하는 스킬 관리 서비스정본이 Git과 DB 두 곳이 됨. 리뷰·이력·CODEOWNERS를 다시 만들어야 함Git + CI + index.json. 필요하면 읽기 전용 카탈로그 화면만 Hub에 추가
처음부터 Kafka·서비스 메시운영 부담이 사용자 수·이벤트 양에 비해 큼폴링 + DB. 사내 표준 버스가 있으면 그때 합류
실행 기록에 화면 내용·표 값 원문 수집업무 데이터가 서버에 쌓여 보안 범위가 커짐요약만 수집. 문제 분석은 사용자가 내보낸 진단 보고서(값 가림)로
서버가 PC로 명령을 밀어 넣는 구조(PC 인바운드 포트)PC 방화벽·보안 프로그램과 충돌, 공격 면 확대PC가 서버로 폴링/장기 연결
