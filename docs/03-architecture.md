# 03. 아키텍처 설계서

> 문서 상태: 초안 (v0.1, 2026-10-13)

## 1. 설계 원칙

1. **화면은 텍스트로 읽는다.** 스크린샷 좌표 클릭이 아니라 DOM/접근성 트리를 요소 번호가 붙은 텍스트로 줄여 모델에 준다. 모델은 번호만 고른다.
2. **흐름은 스킬이 쥔다.** 모델이 자유롭게 계획하지 않는다. 스킬 문서의 단계를 따라가며 단계별 판단만 한다.
3. **데이터는 모델을 거치지 않는다.** 표 데이터는 PC 안의 데이터셋으로 보관하고, 모델에는 컬럼 구조와 샘플만 준다. 가공은 로컬 엔진이 실행한다.
4. **되돌릴 수 없는 동작은 사람이 승인한다.**
5. **서버 없이도 돈다.** 실행에 필요한 것은 사용자 PC와 사내 Gemma API뿐이다. 중앙 서버는 관리 편의를 위한 선택 요소다.

## 2. 전체 구성

```
┌──────────────────────── 사용자 PC ────────────────────────┐
│                                                           │
│  ┌──────────── Chrome / Edge ────────────┐                │
│  │  크롬 확장 (MV3)                       │                │
│  │  ├ Side Panel   대화, 진행 표시, 승인   │                │
│  │  ├ Service Worker  에이전트 루프(P1~2) │                │
│  │  └ Content Script  스냅샷, 동작 실행    │                │
│  │           │                            │                │
│  │   [사내 웹 시스템 탭]  ← 사용자 세션     │                │
│  └───────────┬───────────────────────────┘                │
│              │ Native Messaging (P3~)                     │
│  ┌───────────┴───────────────────────────┐                │
│  │  데스크탑 클라이언트 (Electron, P3~)    │                │
│  │  에이전트 루프 · 스킬 저장소 · 스케줄러  │                │
│  │  파일/엑셀 · 감사 로그(SQLite)          │                │
│  └───────────┬───────────────────────────┘                │
└──────────────┼────────────────────────────────────────────┘
               │ HTTPS (사내망)
     ┌─────────┼──────────────┬─────────────────────┐
     ▼         ▼              ▼                     ▼
 사내 Gemma  사내 Git      배포 파일 서버        Hub 서버 (P3~, 선택)
   API      (스킬 저장소)  (확장·클라이언트 업데이트) (정책·로그·통계)
```

### 단계별 구성 차이

| | Phase 1~2 | Phase 3 이후 |
|---|---|---|
| 에이전트 루프 위치 | 확장 Service Worker | 데스크탑 클라이언트 |
| 파일 접근 | 사이드 패널의 파일 선택, 다운로드 폴더 | 지정 폴더 직접 접근 |
| 스킬 배포 | 확장에 번들 + 로컬 폴더 | 사내 Git 동기화 |
| 로그 | 확장 로컬 저장 | SQLite + Hub 수집 |
| 스케줄 | 없음 | 클라이언트 스케줄러 |

에이전트 코어는 처음부터 별도 패키지로 만들어 확장과 클라이언트가 같은 코드를 쓴다. Phase 3에서 위치만 옮긴다.

## 3. 컴포넌트

### 3.1 크롬 확장

| 모듈 | 역할 |
|---|---|
| Side Panel (React) | 대화, 단계 진행 표시, 승인 대화상자, 결과 미리보기, 스킬 목록 |
| Service Worker | 탭 관리, 메시지 라우팅, (P1~2) 에이전트 루프 실행 |
| Content Script | 페이지 스냅샷 생성, 클릭·입력 실행, 그리드 추출·입력 |
| CDP 브리지 | `chrome.debugger`로 신뢰성 있는 입력 이벤트, iframe 접근, 스크린샷 |
| 사이트 어댑터 | 특정 UI 프레임워크의 그리드 추출·입력 전용 로직 (플러그인 방식) |

### 3.2 에이전트 코어 (공용 패키지)

| 모듈 | 역할 |
|---|---|
| Loop | 관찰 → 판단 → 실행 → 검증 반복, 중단 조건 관리 |
| LLM Client | Gemma API 호출, 스키마 검증, 재시도, 토큰 예산 관리 |
| Skill Runtime | 스킬 로딩·선택, 단계 추적, 검증 조건 평가 |
| Tool Registry | 도구 정의와 실행기 연결, 위험 등급 판정 |
| Policy Guard | 허용 도메인, 스킬 선언 범위, 입력값 정책 검사, 승인 게이트 |
| Path Cache | 성공한 요소 경로 저장·재생 |
| Dataset Store | 표 데이터 보관, 핸들 발급, 샘플 제공 |
| Transform Engine | 가공 명세 실행 (필터, 정렬, 집계, 파생, 조인) |
| Audit Logger | 단계별 기록 |

### 3.3 데스크탑 클라이언트 (Phase 3)

Electron 앱. 에이전트 코어를 내장하고 확장과 Native Messaging으로 통신한다. 추가 기능은 폴더 접근, 스케줄러, 스킬 Git 동기화, 자동 업데이트, 트레이 상주.

### 3.4 Hub 서버 (Phase 3, 선택)

단일 VM 또는 컨테이너 1개로 충분하다. Node 서비스 하나와 PostgreSQL(또는 SQLite).

- 정책 배포: 허용 도메인, 금지 동작, 모델 엔드포인트, 최소 지원 버전
- 감사 로그 수집
- 사용 통계 대시보드: 스킬별 실행 수, 성공률, 소요 시간

Hub가 내려가도 PC는 마지막으로 받은 정책으로 계속 동작한다.

## 4. 에이전트 루프

```
요청 수신
  └ 스킬 선택 (사용자 지정 또는 모델 제안 → 사용자 확인)
      └ 입력값 확보 (부족하면 질문)
          └ 단계 반복:
              ① 관찰   화면 스냅샷 생성
              ② 판단   캐시된 경로가 있으면 사용, 없으면 모델 호출
              ③ 검사   Policy Guard (도메인, 위험 등급, 입력값 정책)
              ④ 승인   R3이면 사용자 승인 대기
              ⑤ 실행   도구 실행
              ⑥ 검증   단계의 verify 조건 확인
                       실패 → 재관찰 후 1회 복구 시도 → 실패 시 중단 보고
          └ 결과 정리, 로그 기록
```

### 4.1 화면 스냅샷

보이는 요소 중 상호작용 가능하거나 의미 있는 것만 뽑아 번호를 붙인다.

```
[page] 재공 현황 조회 — https://mes.example.internal/wip
[1] combobox "라인" value="8라인"
[2] combobox "공정" value=""
[3] textbox "제품코드"
[4] button "조회"
[5] grid "재공 목록" rows=128 cols=[Lot ID, 제품, 공정, 수량, 정체시간]
[6] button "엑셀"
```

- 그리드는 내용 대신 **요약**(행 수, 컬럼명)만 넣는다. 내용은 `extract_table`로 데이터셋에 담는다.
- 비밀번호 필드, 숨김 필드는 제외한다.
- 스냅샷이 토큰 예산을 넘으면 스킬의 현재 단계와 관련된 영역 위주로 줄인다.

### 4.2 도구 목록

| 도구 | 설명 | 등급 |
|---|---|:-:|
| `navigate(url)` | 허용 도메인 내 이동 | R0 |
| `snapshot()` | 화면 다시 읽기 | R0 |
| `click(ref)` | 요소 클릭. 대상이 저장/상신 계열이면 R3로 승격 | R0/R3 |
| `type(ref, text)` / `select(ref, value)` | 값 입력 | R2 |
| `wait_for(condition)` | 요소·텍스트 등장 대기 | R0 |
| `extract_table(ref)` → dataset | 그리드를 데이터셋으로 추출 | R0 |
| `paste_table(ref, dataset, mapping)` | 그리드에 일괄 입력 | R2 |
| `download(ref)` → file | 다운로드 버튼 클릭 후 파일 확보 | R1 |
| `read_excel(file, sheet)` → dataset | 엑셀 읽기 | R0 |
| `transform(dataset, spec)` → dataset | 가공 명세 실행 | R0 |
| `compare(datasetA, datasetB)` | 두 데이터셋 대조 | R0 |
| `write_excel(datasets, path)` | 엑셀 저장 | R1 |
| `ask_user(question)` | 사용자에게 질문 | - |
| `request_approval(summary)` | 승인 요청 | - |
| `finish(result)` / `abort(reason)` | 종료 | - |

`click`의 R3 승격은 스킬에 선언된 제출 단계와 버튼 라벨 규칙(저장, 상신, 제출, 삭제, 승인 등)으로 판정한다. 모델 판단에 맡기지 않는다.

### 4.3 데이터 처리 경로

```
웹 그리드 ──extract_table──▶ Dataset Store ──transform──▶ Dataset ──write_excel──▶ 파일
                                  │
                                  └─ 모델에는 { columns, rowCount, sample 5행 }만 전달
```

가공 명세는 선언형 JSON이다. 모델이 임의 코드를 만들어 실행하지 않는다.

```json
{
  "steps": [
    { "op": "filter", "where": "정체시간 >= 24" },
    { "op": "group", "by": ["공정"], "agg": { "수량": "sum", "Lot ID": "count" } },
    { "op": "sort", "by": "수량", "desc": true }
  ]
}
```

### 4.4 경로 캐시

단계가 검증까지 통과하면 `(스킬 ID, 단계 번호, 페이지 식별자)` 키로 요소 선택자와 동작을 저장한다. 다음 실행은 캐시부터 시도하고, 요소가 없거나 검증에 실패하면 캐시를 버리고 모델을 호출한다. 실행이 반복될수록 모델 호출이 줄어 빨라지고 결과가 일정해진다.

## 5. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript | 확장·클라이언트·코어가 한 언어 |
| 저장소 구조 | pnpm 모노레포 | `core`, `extension`, `desktop`, `hub`, `skills` 패키지 분리 |
| 확장 | Manifest V3, WXT, React | Side Panel, 핫리로드, Chrome/Edge 동시 빌드 |
| UI | React, Tailwind | |
| 브라우저 제어 | Content Script + `chrome.debugger`(CDP) | 사용자 세션을 그대로 사용 |
| 데스크탑 | Electron, electron-builder | Node 라이브러리 그대로 사용, MSI 생성, 자동 업데이트 |
| 확장↔클라이언트 | Native Messaging | 포트를 열지 않아 보안 심사에 유리 |
| LLM 연동 | OpenAI 호환 HTTP 클라이언트 | 사내 API 형식에 맞춰 어댑터 1개 |
| 출력 검증 | Zod | 툴 호출 스키마 검증·재시도 |
| 엑셀 | ExcelJS (읽기/쓰기), SheetJS (형식 호환) | |
| 가공 엔진 | Arquero 또는 DuckDB-WASM | 선언형 명세를 실행 |
| 로컬 저장 | 확장: IndexedDB / 클라이언트: SQLite | |
| 스킬 형식 | Markdown + YAML frontmatter | 현업이 직접 작성 |
| 스킬 저장소 | 사내 Git | 리뷰·버전·이력을 기존 도구로 해결 |
| Hub | Node(Fastify) + PostgreSQL | 단일 인스턴스 |
| 테스트 | Vitest, Playwright(확장 E2E), 모의 사이트 | |

외부 오픈소스 에이전트(browser-use, Stagehand 등)를 그대로 쓰지 않는 이유는, 이들이 별도 브라우저를 띄우거나 디버깅 포트를 요구해 사내 SSO 세션과 보안 정책에 맞추기 어렵기 때문이다. 화면 스냅샷 방식 등 설계는 참고한다.

## 6. 배포·운영

쿠버네티스 같은 서비스 인프라는 필요 없다. 실행은 모두 사용자 PC에서 일어나고, 중앙에는 파일 서버와 (선택적으로) 작은 Hub 하나만 둔다.

### 6.1 배포

| 대상 | 방식 |
|---|---|
| 크롬 확장 | 사내 파일 서버에 `.crx`와 `update.xml` 게시 → 브라우저 정책(`ExtensionInstallForcelist`)으로 대상 PC에 강제 설치·자동 업데이트 |
| 데스크탑 클라이언트 | 서명된 MSI → 사내 소프트웨어 배포 도구로 설치, 이후 `electron-updater`가 사내 파일 서버에서 업데이트 |
| 스킬 | 사내 Git 저장소 `main` 브랜치 → 클라이언트가 주기적으로 동기화 |
| 정책 | Phase 1~2: 확장에 내장된 설정 파일 / Phase 3~: Hub에서 내려받음 |

### 6.2 릴리스 채널

`canary`(개발팀) → `pilot`(파일럿 부서) → `stable`(전체). 채널별로 `update.xml` 경로를 달리해 단계 배포한다. 문제가 생기면 이전 버전 파일을 다시 게시해 되돌린다.

### 6.3 운영

| 항목 | 내용 |
|---|---|
| 모니터링 | 스킬별 성공률·소요 시간·실패 사유. 성공률이 떨어진 스킬은 화면 변경 가능성이 높으므로 스킬 오너에게 알림 |
| 스킬 유지보수 | 화면 변경 시 스킬 문서만 수정해 Git으로 배포. 확장 재배포 불필요 |
| 장애 대응 | 원격 정책으로 특정 스킬 또는 전체 기능을 즉시 비활성화 (kill switch) |
| 모델 변경 | Gemma 버전이 바뀌면 회귀 테스트 세트(스킬별 기록된 화면)로 검증 후 전환 |
| 지원 | 실행 로그 내보내기 기능으로 문의 시 재현 자료 확보 |

### 6.4 필요한 인프라 요약

| 자원 | 규모 | 시점 |
|---|---|---|
| 사내 Gemma API 사용 권한·할당량 | 기존 제공분 | Phase 0 |
| 사내 Git 저장소 | 2개 (코드, 스킬) | Phase 1 |
| 정적 파일 서버 | 기존 사내 서버의 경로 하나 | Phase 2 |
| 코드 서명 인증서 | 사내 인증서 | Phase 2 |
| Hub 서버 | VM 1대 | Phase 3 |

## 7. 보안 설계

| 위협 | 대응 |
|---|---|
| 페이지 내용에 섞인 지시문(프롬프트 인젝션) | 페이지 텍스트는 데이터 영역으로 구분해 전달, 스킬이 선언한 도메인·도구 밖의 동작은 Policy Guard가 차단 |
| 잘못된 제출 | R3 승인 게이트, 제출 전 화면 값 대조 |
| 과도한 방화벽 신청 | 입력값 정책 검증 (전체 대역, any 포트, 기간 초과 차단), 기존 결재 유지 |
| 데이터 유출 | 사내 Gemma API만 호출, 데이터셋은 모델에 미전달, 외부 도메인 접근 차단 |
| 권한 오남용 | 사용자 세션 안에서만 동작, 서비스 계정 없음, 감사 로그 |
| 변조된 스킬 | Git 리뷰 승인 필수, 클라이언트는 지정 저장소·브랜치만 신뢰 |
| 변조된 프로그램 | 코드 서명, 정책 기반 설치 |

## 8. 미결정 사항 (Phase 0에서 확정)

| 항목 | 확인 내용 | 결과에 따른 분기 |
