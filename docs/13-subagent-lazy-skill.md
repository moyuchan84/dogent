# 13. 서브에이전트와 스킬 지연 로딩 (설계)

> 문서 상태: v0.2 (2026-10-20) · 1단계(지연 로딩 일부)와 `run_skill` 구현됨. `delegate`, 도구 묶음, `skill_ref`는 아직
> 관련: [09-client-architecture.md](09-client-architecture.md) D6(안전장치는 확장), D7(스킬 폴더), [05-skill-spec.md](05-skill-spec.md)

Claude Agent SDK의 서브에이전트와 스킬 점진 공개(progressive disclosure)를 Gemma급 작은 모델에 맞게 옮긴다.
목표는 둘이다: **모델이 한 번에 보는 글을 줄이고**, **긴 일을 작은 일로 나눠 맡긴다.**

## 1. 지금 상태 (코드 기준)

| 항목 | 현재 | 문제 |
|---|---|---|
| 스킬 고르기 | `shortlistSkills`(최대 20개) → `planRequest`가 후보 전부의 입력 설명까지 한 프롬프트에 넣고 한 번에 고름 | 후보가 많으면 입력 설명이 길어져 Gemma가 고르기와 값 뽑기를 한꺼번에 못 한다 |
| 차례마다 보내는 글 | `AGENT_SYSTEM_PROMPT`(도구 설명 전부) + 스킬 본문 전체 + 지금 할 단계(본문과 중복) | 스킬이 길수록, 단계가 뒤로 갈수록 필요 없는 글이 매 차례 따라간다 |
| 한 실행에서 쓰는 스킬 | 하나. 자유 요청(`buildFreeSkill`)은 기존 스킬을 부를 수 없다 | "조회해서 엑셀로 정리"처럼 두 스킬에 걸친 요청은 스킬 없이 처음부터 모델이 푼다 |
| 컨텍스트 | 동작 기록은 최근 15개만 | 긴 일은 앞 내용을 잃고, 큰 화면 글이 계속 쌓인다 |

## 2. 스킬 지연 로딩

스킬 정보를 네 층으로 나누고, 필요한 층만 모델에 보인다. (디스크 읽기는 지금처럼 한 번에 해도 된다. 줄이려는 것은 프롬프트다.)

| 층 | 내용 | 모델에 보이는 때 |
|---|---|---|
| L0 색인 | `id: 이름 — 설명` 한 줄 (태그 포함 검색은 코드가 함) | 스킬을 고를 때 |
| L1 입력 | 고른 스킬의 `inputs`(설명, 기본값, 보기) | 값을 뽑을 때, 그 스킬 것만 |
| L2 본문 | 단계 절차 | 실행 중 **지금 단계만 전문**, 나머지는 한 줄 개요 |
| L3 참고 | `skills/<id>/refs/*.md` (화면 용어집, 코드표 등) | 모델이 `skill_ref`로 요청할 때만 |

### 변경 4가지

1. **계획을 두 단계로 나눈다** (`planner.ts`)
   - 1단계: L0 색인만 보고 `skill_id` 고르기. 후보를 20개 → 30개로 늘려도 프롬프트가 짧다.
   - 2단계: 고른 스킬의 L1만 보고 값 뽑기. 스킬이 없으면(`null`) 2단계는 건너뛴다.
   - 모델 호출이 1번 → 2번이 되지만 각각 짧고, 실패를 어느 단계 탓인지 구분할 수 있다.
2. **본문을 단계 창으로 보낸다** (`prompt.ts` `buildTurnMessages`)
   - 보내는 것: 스킬 머리(이름, 도메인, 입력값), 개요(`1. 제목…` 한 줄씩), **지금 단계 전문**, `예외`·`결과` 절(모든 단계에 적용되므로 항상).
   - 빼는 것: 다른 단계의 도구·인자 줄. 인자는 "한 글자도 바꾸지 않고 쓴다"는 규칙이 있어 지금 단계 것만 있으면 충분하다.
   - 검사 줄·`{out.이름}` 치환은 지금처럼 루프가 한다.
3. **도구 설명을 묶음으로 나눈다** (`prompt.ts`)
   - 묶음: `core`(click·type·select·next_step·finish·ask_user·abort), `table`(extract/fill/download/transform/write_excel), `tabs`(open/switch/close/tab_list), `text`(read_text·summarize), 그리고 지금처럼 `office`·`tools`(MCP).
   - **어떤 묶음을 넣을지는 모델이 아니라 코드가 정한다.** 스킬 본문이 쓰는 도구(lint가 이미 도구를 읽는다) + 자유 요청이면 요청 글의 단서(`officeIntent`처럼). 모르면 전부 넣는다(현재와 같음).
   - 빠진 묶음의 도구를 모델이 부르면 "이 실행에서 쓸 수 없는 도구"로 막고 목록을 알려 준다.
4. **참고 파일** (선택, 2차)
   - `client/src/skills.ts`가 `refs/`의 파일 이름만 읽어 `Skill`에 `refs: string[]`로 담고, 본문은 열 때 읽는다.
   - 새 도구 `skill_ref {name}`: 4000자까지 돌려준다 (`read_text`와 같은 `clipText`).

### 먼저 잴 것
`llm.complete` 호출마다 보낸 글자 수(시스템/사용자)와 응답 시간을 `RunEvent`의 `llm_usage`로 남긴다. 실제 스킬(`wip-check`, `firewall-request`)과 `mock-llm`으로 전후를 비교해, 줄어든 만큼이 없으면 2·3번은 되돌린다. 위 효과는 아직 추정이다.

**1단계 구현 결과 (2026-10-20)**: `llm_usage` 이벤트, `outlineSteps`(단계 개요), 후보 8개 초과 시 계획 2단계(`TWO_STAGE_MIN`)가 들어갔다. 기본 제공 스킬 6개의 본문은 단계 개요 + 지금 단계 합계로 약 30~55% 줄었다(예: wip-check 2438자 → 1112자). 하지만 본문은 차례마다 3~5천자 가는 글 중 일부일 뿐이고, 시스템 프롬프트(도구 설명)가 약 3800자(+엑셀 770자, MCP 도구 설명)로 더 크다. 그래서 도구 묶음(2단계)의 효과는 실모델 계측 뒤에 정한다. 실모델 전후 비교는 아직 하지 않았다.

## 3. 서브에이전트

### 정의
부모 실행이 일을 **별도 컨텍스트의 자식 실행**에 맡기고, 부모는 짧은 결과만 받는다. 코드로는 `runSkill`을 안에서 한 번 더 부르는 것이다 (`runSkill`이 이미 `RunDeps`만으로 독립 동작한다).

### 두 종류

| | `run_skill` | `delegate` |
|---|---|---|
| 하는 일 | 이름 있는 스킬을 입력값과 함께 실행 | 목표 한 줄을 자유 요청으로 실행 |
| 인자 | `{"id", "inputs"}` | `{"goal", "tools": ["web"\|"excel"\|"mcp"…], "site"}` |
| 절차 | 스킬이 정함 (검사·경로 기억 모두 그대로) | `buildFreeSkill`로 만든 한 단계 스킬 |
| 쓰기(저장·상신) | 스킬의 `risk`가 허용하는 만큼 | **항상 불가** (`allowWrite=false`로 고정). 읽기·가공 전용 |
| 1차 구현 | ● | 2차 |

`run_skill`은 스킬 단계에 **직접 단계**(도구와 인자가 적힌 줄)로도 쓸 수 있다. 그러면 모델 없이 스킬이 스킬을 부르는 조합이 된다.

```
3. run_skill {"id": "wip-check", "inputs": {"line": "{line}"}}
   - 확인: 데이터셋 wip 행 수 > 0
```

### 안전 규칙 (부모보다 넓어질 수 없다)

D6에 따라 통제는 확장이 지키지만, 클라이언트 쪽에서도 자식이 부모를 우회하지 못하게 한다.

1. **깊이 1**: 자식은 `run_skill`·`delegate`를 쓸 수 없다. 스킬 간 순환 호출은 lint에서 막는다 (새 규칙, E-번호는 `docs/06` 표에 이어서).
2. **쓰기 권한 상속**: 자식 스킬의 `risk`가 R3인데 부모 실행의 `allowWrite`가 꺼져 있으면 시작하지 않는다. 승인은 같은 `ui.approve`를 거치고 `submit_steps`·`submit_labels`는 자식 스킬 것을 그대로 쓴다. `dryRun`도 상속.
3. **도메인 교집합**: 자식 도메인이 부모가 허용한 호스트(`domains` + `extraHosts`) 밖이면 시작하지 않는다.
4. **예산 공유**: 자식의 `max_steps`·`timeout_sec`는 min(자식 선언, 부모 남은 값). 자식이 쓴 동작 수·시간은 부모에서 뺀다. `abort`(중지) 신호도 전달.
5. **입력 검증**: 자식 시작 전에 `resolveInputs` + `checkInputRules`를 부모 모델이 준 값에 적용 (틀리면 부모에게 실패로 돌려주고 자식은 시작하지 않음).
6. **한 번에 하나**: 브라우저(탭)는 하나뿐이라 병렬 실행은 하지 않는다. 자식이 탭을 열었으면 끝날 때 부모가 보던 탭으로 되돌린다.

### 컨텍스트 격리

- 자식의 `history`·화면 글은 부모에 들어가지 않는다. 부모 기록에는 `run_skill` 한 줄만 남는다: `#4 run_skill {...} → 성공: <결과 요약 1500자 이내>`.
- 자식이 만든 **데이터셋은 공유**한다 (같은 `DatasetStore`). 이름이 겹치면 자식 것이 덮어쓰지 않도록 실패 처리하고 부모에게 알린다. 값만 필요한 경우를 위해 자식의 `outputs`(`{out.이름}`)도 부모 `outputs`에 `자식id.이름`으로 합친다.
- 자식 실행은 `PathMemo`(경로 기억)를 자기 스킬 기준으로 쓴다.

### 구현 결과 (2026-10-20, `run_skill` 1차)

`run_skill`만 구현했다. `delegate`와 `skill_ref`는 아직이다. 위 안전 규칙은 `src/core/subagent.ts`의 `prepareChild`가 시작 전에 검사한다 (`tests/subagent.test.ts`).

- 규칙 1 깊이: `RunDeps.depth`. 불린 스킬 안에서는 `skills` 통로를 주지 않고 `prepareChild`도 거절한다.
- 규칙 2 쓰기 권한: 자식이 R3인데 부모가 R3가 아니면 거절. 승인과 `dryRun`은 같은 `ui`와 `deps`를 물려받는다. 부모가 `dryRun`으로 멈추면 `end: 'dryrun'`이 전해진다.
- 규칙 3 도메인: `coversDomains`. 자식의 도메인 패턴이 모두 부모의 패턴 안에 들어야 한다.
- 규칙 4 예산: 자식의 `max_steps`·`timeout_sec`를 부모의 남은 값으로 줄인다. 자식이 쓴 동작 수는 부모의 한도에서 뺀다 (`childActions`). 중지 신호는 `deps.signal`로 같이 간다.
- 규칙 5 입력: `resolveInputs`(정책 규칙 포함)를 자식 시작 전에 적용한다. 파일 입력이 있는 스킬은 부를 수 없다.
- 규칙 6 한 번에 하나, 탭 복귀: 순차 실행이고, 자식이 끝나면 부모가 보던 탭으로 되돌린다 (같은 탭 안에서 주소가 바뀐 것은 되돌리지 못한다).
- 데이터셋: 자식은 자기 `DatasetStore`를 쓰고, 끝난 뒤 부모에 합친다. 이름이 겹치면 `이름_2`처럼 바꿔 담고 결과 요약에 알린다 (문서 초안의 "겹치면 실패"에서 바꿈. 자식이 이미 일을 마친 뒤라 버리는 것보다 낫다고 판단).
- 기록: 자식의 `outputs`는 `스킬id_이름`(하이픈은 `_`)으로 부모에 합친다.
- 이벤트: `sub_start`/`sub_action`/`sub_end`. 자식의 `action`·`end`는 부모의 것과 섞이지 않게 다시 내보내지 않는다 (그러지 않으면 "스킬로 저장"이 자식의 동작을 부모 동작으로 저장한다).
- 안내: 모델에게 `run_skill` 목록을 보여 주는 것은 **자유 요청뿐**이다 (`부를 수 있는 스킬` 상위 8개). 정해진 스킬은 `run_skill로 ... \`{"id": ..., "inputs": {...}}\`` 직접 단계로 부른다.
- lint: `run_skill` 인자 형식을 보고, 그 단계 뒤로는 데이터셋 존재 검사(E05)를 하지 않는다 (자식이 만드는 이름을 알 수 없어서). id 존재·순환 검사는 카탈로그가 필요해 아직 없다 (깊이 1 제한이 순환을 막는다).
- 알려진 한계: 자유 요청이 보는 탭의 호스트와 다른 사이트의 스킬은 목록에 나오지 않는다. 요청에 시스템 이름·주소를 쓰면 `extraHosts`로 허용 도메인에 들어가 부를 수 있다.

### 코드 배치

| 파일 | 변경 |
|---|---|
| `src/core/subagent.ts` (신규) | `runChild(parent, spec)`: 규칙 1~6 검사 → `runSkill` 호출 → 결과 요약. 순수 core, UI·클라이언트 의존 없음 |
| `src/core/actions.ts` | 액션 스키마에 `run_skill`, (2차) `delegate`, `skill_ref` 추가. 직접 단계 정규식(110행)에도 `run_skill` 추가 |
| `src/core/loop.ts` | `execute`에 case 추가. `RunDeps.skills?: SkillCatalogPort` (`get(id)`, `list()`), `RunDeps.depth` |
| `src/core/types.ts` | `SkillCatalogPort`, `RunEvent`에 `sub_start`/`sub_end`(자식 id, 깊이) |
| `src/core/prompt.ts` | `SUBAGENT_PROMPT`: `OFFICE_PROMPT`처럼 `skills`가 있을 때만 덧붙임. L0 색인 몇 줄(상위 5개)만 같이 보여 줌 |
| `src/core/lint.ts` | `run_skill`의 id 존재·입력 이름·순환 검사 |
| `client/src/session.ts` | `execute`에서 `skills` 포트를 `this.skills`로 연결. 화면(터미널·데스크탑)은 `sub_start`로 들여쓰기 |

### 모델에게 보이는 모습 (자유 요청, Gemma)
```
요청: "7라인 재공 확인해서 HOLD만 엑셀로 정리"
#1 run_skill {"id":"wip-check","inputs":{"line":"7라인"}} → 성공: 데이터셋 wip(132행)
#2 transform {...HOLD만...} → 성공
#3 write_excel {...} → 성공
```
부모는 화면 조작 수십 동작 대신 3개 동작만 본다.

## 4. 순서

| 단계 | 내용 | 위험 |
|---|---|---|
| 0 | 현재 작업 트리(`feature/tool-registry`의 미커밋 변경)를 정리해 커밋. 같은 파일(`loop.ts`, `prompt.ts`, `actions.ts`, `types.ts`)을 건드리므로 겹치지 않게 | — |
| 1 | `llm_usage` 계측 + 스킬 단계 창 + 계획 2단계 | 낮음. 계측값으로 효과 확인 |
| 2 | 도구 묶음 | 중간. 모를 때 전부 넣는 안전 기본값 유지 |
| 3 | `run_skill` + `subagent.ts` + lint + 직접 단계 | 중간. 안전 규칙 테스트 필수 |
| 4 | `delegate`(읽기 전용), `skill_ref` | 낮음 |
| 5 | (보류) 병렬 서브에이전트, 쓰기 가능한 `delegate`, 요청을 하위 작업으로 쪼개는 계획기 | 탭 하나 제약과 승인 흐름 때문에 별도 설계 |

## 5. 시험 계획

`tests/run.test.ts`와 `tests/helpers.ts`의 스크립트 LLM 방식을 따른다.

- **지연 로딩**: 단계 창 프롬프트에 다른 단계의 인자가 없고 `예외`·`결과`는 있다 / 2단계 계획기가 후보 30개에서 L0만 보낸다 / 묶음에 없는 도구 호출은 막힌다.
- **서브에이전트**: 깊이 2 차단 / R3 자식 + `allowWrite` 꺼짐 → 시작 안 함 / 도메인 밖 자식 거부 / 예산 차감과 중지 전파 / 데이터셋 공유와 이름 충돌 / 결과 1500자 절단 / 자식 실패가 부모에 실패로 전달되고 `MAX_STRIKES`에 포함 / 직접 단계 `run_skill` / 순환 lint.
- **e2e**: `tools/mock-llm.mjs`에 "조회 스킬 → 가공 → 저장" 시나리오 추가 (`tests/e2e/client.e2e.mjs`).
