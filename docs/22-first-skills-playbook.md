# 22. 첫 업무 스킬 만들기 플레이북 (조회 1건 + 쓰기 1건)

> 문서 상태: v0.1 (2026-11-03)
> 관련: [06-skill-authoring.md](06-skill-authoring.md) (제작 체계), [05-skill-spec.md](05-skill-spec.md) (명세), [04-roadmap.md](04-roadmap.md) (합격 기준), [19-project-status-and-checklist.html](19-project-status-and-checklist.html) (확인 목록)

사내 업무 스킬이 아직 하나도 없다 (docs/19 G3). 이 문서는 **첫 업무 2건**(읽기 1, 쓰기 1)을 고르고, 만들고, 합격시키는 순서를 한 장으로 정리한 것이다. 사내 화면이 있어야 끝낼 수 있는 일이라 코드가 아니라 절차로 만들었다.

## 1. 원칙

1. **읽기 먼저, 쓰기는 그다음.** 조회(R1) 스킬로 화면 읽기·모델·승인 흐름이 되는지 확인한 뒤 쓰기(R3)에 들어간다.
2. **한 번에 한 시스템.** 첫 두 건은 같은 시스템에서 고르면 화면 점검·사전·사이트 허용을 한 번만 하면 된다.
3. **쓰기는 시험 실행부터.** 처음 열 번은 모두 `--dry-run`(상신 직전 멈춤)으로 한다. 실제 상신은 현업 담당자가 옆에서 볼 때만.
4. **측정한다.** 20회 반복 성공률과 값 일치를 기록으로 남긴다 (7절 양식). 기분으로 "잘 된다"고 하지 않는다.

## 2. 업무 고르기

후보마다 점수(0~2)를 매겨 높은 것을 고른다.

| 기준 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 빈도 | 월 몇 번 | 주 몇 번 | 매일 |
| 건당 수작업 시간 | 5분 미만 | 5~20분 | 20분 이상 |
| 화면 읽힘 (화면 점검 결과) | canvas·shadow DOM·읽지 못한 iframe | 머리글 없는 표 등 경고 | 문제 없음 |
| 입력이 바뀌는 정도 | 매번 다 다름 | 값 3~5개가 바뀜 | 값 1~2개 (라인, 날짜 등) |
| 규칙이 글로 있나 | 사람마다 다름 | 대체로 있음 | 문서·정책으로 있음 |
| 담당자 협조 | 연락이 안 됨 | 가끔 | 같이 시험해 줄 수 있음 |

- 읽기 후보: 목록·현황 조회 후 엑셀로 받기 (예: 재공 조회, 홀드 Lot 목록). 합계가 0~3점이면 미룬다.
- 쓰기 후보: **규칙이 분명한 신청**(예: IP 방화벽 신청). 입력값 정책을 글로 쓸 수 있는 것을 고른다. 되돌릴 수 없는 일(삭제, 결재 확정)은 첫 건으로 고르지 않는다.
- 화면 읽힘이 0점인 업무는 스크린샷 보조(docs/17 P1-1)나 화면의 엑셀 내려받기가 먼저다.

## 3. 현업 인터뷰 시트 (업무마다 한 장)

현업 담당자와 함께 채운다. 이 시트가 곧 스킬의 설명·입력·검사 조건이 된다.

```
업무 이름:
시스템 (사전 id):            사이트 주소:
언제, 왜 하나 (빈도, 결과를 어디에 쓰나):
현재 수작업 순서 (메뉴 경로부터 화면별로):
  1.
  2.
입력값 (이름, 설명, 예시, 허용 범위):
  -
결과물 (엑셀 열 이름, 어디에 저장, 보고 대상):
저장·상신이 있나 (버튼 이름, 되돌릴 수 있나, 누가 승인하나):
금지·주의 (넣으면 안 되는 값, 하지 말아야 할 조작):
자주 생기는 예외 (화면 팝업, 권한 오류, 데이터 없음):
수작업 건당 시간 / 월 건수:
시험해 줄 담당자:
```

## 4. 만드는 순서

| 단계 | 할 일 | 도구 | 끝났다고 보는 기준 |
|---|---|---|---|
| 1 | 화면 점검 | 사이드 패널 **화면 점검** | 보고서에 막히는 곳 없음 (있으면 조치 후 다시) |
| 2 | 사이트 허용 | **이 사이트 허용** (회사 빌드는 목록 방식) | 점검에서 "허용 목록 밖" 경고가 사라짐 |
| 3 | 시스템 사전 `draft` 등록 | `docs/18`의 절차 (`status: draft`) | `dogent systems`에 `[공용]`으로 보임. 별칭으로 요청해도 찾아짐 |
| 4 | 자유 요청으로 한 번 | `dogent "<업무를 말로>"` | 결과가 나옴. 안 되면 화면 점검·모델 문제부터 (확인 목록 C5, C9) |
| 5 | 스킬 초안 | **+ 말로 스킬 만들기** 또는 **스킬 만들기**(녹화), 또는 잘 된 4번을 "스킬로 저장" | 초안이 생김 |
| 6 | 품질 검사 | `dogent check <SKILL.md>` | 등급 **B 이상**, 오류 0 |
| 7 | 시험 실행 | 앱의 시험 실행 또는 `dogent run <id> … --dry-run` | 쓰기 스킬이 상신 직전에 멈춤, 승인 창 값이 화면과 같음 |
| 8 | 20회 반복 | 7절 기록지 | 8절 합격 기준 충족 |
| 9 | 현업 확인 | 담당자가 결과·시간을 확인 | 담당자 서명(메일 한 줄) |
| 10 | 팀 저장소 PR | `dogent-skills` 저장소 | CI 통과 + CODEOWNERS 승인 → main, `index.json` 갱신 |
| 11 | 시스템 사전 `verified` | 사전 저장소 PR | 담당자가 확인 후 `status: verified` |

## 5. 스킬 작성 요령

- **단계는 목표 문장으로.** "7라인을 고른다", "조회 버튼을 눌러 결과 표가 나올 때까지 기다린다". 클릭 좌표나 요소 번호를 적지 않는다.
- **늘 같은 조작은 빠른 경로로.** 녹화로 만든 동작은 모델 없이 빠르게 돈다. 화면이 바뀌어 실패한 단계만 모델이 다시 찾는다.
- **입력에는 설명과 기본값.** "라인: 조회할 라인 이름 (예: 7라인)" 처럼. 요청에서 값을 뽑는 정확도가 좋아진다.
- **`검사:` 조건을 둔다.** 단계가 끝났다는 증거(결과 표가 보임, 신청 번호가 보임)를 적는다. 없으면 건너뛰어도 모른다.
- **쓰기 단계는 버튼을 선언한다.** 상신 버튼 이름을 스킬에 명시한다(선언한 버튼만 승인 창을 거쳐 눌린다). 사내 버튼 이름이 "상신", "결재요청", "Submit" 중 무엇인지 화면에서 확인해 적는다.
- **입력값 정책(`policy.yaml`)을 쓴다.** 허용 IP 대역, 금지 포트, 사유 최소 글자 수 같은 현업 규칙을 실행 전에 검사한다. 규칙이 글로 없으면 만들지 못한 것이다 (인터뷰 시트의 "규칙").
- **담당 부서(`owner`)와 `tags`를 적는다.** 찾기와 승인 라우팅에 쓰인다.

## 6. 쓰기 업무의 추가 절차

1. 정책 규칙을 담당자에게 받아 `policy.yaml`로 옮기고, **위반 값**(대역 밖 IP, 금지 포트, 짧은 사유)으로 먼저 시험한다. 실행 전에 막혀야 한다.
2. `--dry-run`으로 10회. 매번 상신 직전에 멈추는지, 승인 창의 값이 화면과 같은지 본다.
3. 승인 창을 **일부러 닫아** 본다. 눌리지 않아야 한다.
4. 화면 값을 일부러 바꿔 입력 대조가 어긋나게 해 본다 (입력 후 값이 달라진 경우). 승인 요청이 뜨기 전에 멈춰야 한다.
5. 그다음에야 담당자가 옆에서 보는 상태로 **실제 상신 1건**. 신청 번호가 결과에 기록되는지 확인한다.
6. 실제 상신은 한 번에 한 건씩 늘린다. 묶어 실행(엑셀 행마다)은 단건이 안정된 뒤.

## 7. 반복 시험 기록지

20회를 같은 조건으로 돌리고 한 줄씩 적는다 (`~/.dogent/runs.jsonl`과 앱의 "기록" 탭, `dogent skills info <id>`의 이 PC 성공률로 보조).

| # | 날짜 | 입력값 | 결과 (성공/실패) | 소요 시간 | 값 일치 (화면과 엑셀) | 실패 원인 (화면/모델/값/기타) | 비고 |
|---|---|---|---|---|---|---|---|
| 1 | | | | | | | |
| … | | | | | | | |
| 20 | | | | | | | |

실패한 실행은 앱의 "기록"에서 **내보내기**로 모델 동작 기록을 받아 둔다 (값은 가려서 공유할 수 있다).

## 8. 합격 기준 (docs/04의 PoC·MVP 기준을 첫 업무에 적용)

| 항목 | 읽기 스킬 | 쓰기 스킬 |
|---|---|---|
| 20회 반복 성공률 | 90% 이상 | 90% 이상 (시험 실행 기준) |
| 추출·입력 값이 화면과 일치 | 100% | 100% |
| 승인 없는 제출 | — | **0건** |
| 입력 대조 불일치 상태의 승인 요청 | — | **0건** |
| 건당 시간 | 수작업보다 길지 않음 | 수작업보다 길지 않음 (사람 개입 시간 포함) |
| 품질 등급 | B 이상 | B 이상 |
| 담당자 확인 | 있음 | 있음 + 보안 부서 승인(쓰기 업무, 확인 목록 C8) |

## 9. 실패했을 때

| 증상 | 가능한 원인 | 조치 |
|---|---|---|
| 요소를 못 찾음, 같은 화면 반복 | iframe·canvas·shadow DOM, 이름 없는 요소 | 화면 점검 다시. 막히는 유형이면 스크린샷 보조(P1-1)나 화면의 엑셀 내려받기 |
| 모델이 엉뚱한 버튼을 누름 | 단계 설명이 모호, 후보 요소가 많음 | 단계를 구체적인 목표로, 빠른 경로를 녹화, 사전의 `screens`에 메뉴 경로 보강 |
| JSON 형식 오류가 잦음 | 모델의 JSON 출력 불안정 | `WXT_LLM_JSON_MODE=true` 가능한지 확인 (C5), 시간 제한 배율 조정 |
| 시스템 이름을 못 알아봄 | 별칭 부족 | 사전의 `aliases`에 사람들이 실제 쓰는 말 추가 |
| 로그인 화면에서 멈춤 | 정상 동작 (로그인은 사람이) | 로그인 후 이어짐. 계속 안 이어지면 로그인 호스트 허용 확인 (C11) |
| 승인 창이 안 뜸 | 저장·상신 버튼을 스킬이 선언하지 않음, 버튼 이름 불일치 | 스킬 단계에 버튼 명시 (C12) |
| 값이 화면과 다름 | 그리드가 입력을 걸러냄 | 입력 후 대조가 잡아냄. 붙여넣기 전용 그리드 경로 확인 |
| 어제는 되던 스킬이 실패 | 화면 변경 | "기록" 탭의 연속 실패 표시, 단계 다시 찾기(경로 기억 갱신), 사전의 화면 정보 갱신 |

## 10. 끝난 뒤

- 합격한 스킬 2건을 팀 저장소에 올리고, 사전 항목을 `verified`로 바꾼다.
- 측정 기록으로 **건당 절감 시간**을 계산한다: (수작업 건당 시간 − 사람 개입 시간) × 월 건수 (docs/04 8절).
- 다음 후보는 2절의 점수표에서 고르고, 같은 시스템의 이웃 업무부터 늘린다.
- 이 과정에서 반복해서 막히는 곳(예: canvas 그리드, 파일 첨부, xls)을 모아 docs/19의 보완 항목 순서를 정한다.
